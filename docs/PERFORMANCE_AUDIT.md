# Аудит продуктивності: Windows Learning Desktop

Ціль перевірки — планшет UNOWHY Y10G001S4M_EEA (MT8167B, 4× Cortex-A35 до 1,3 ГГц, 2 ГБ RAM, Android 9 / API 28).

## Підтверджена архітектура

* Інтерфейс написано Kotlin з Jetpack Compose та Material 3. `DesktopViewport` додає горизонтальну прокрутку для портретного режиму.
* Paint — Compose `Canvas` разом з `android.graphics.Bitmap` і `Canvas`.
* Word використовує звичайний `EditText` через Compose `AndroidView`; Блокнот використовує Compose `OutlinedTextField`.
* Офлайн-браузер — `WebView` через `AndroidView` і локальні HTML-ресурси у `assets`.
* Стан файлової системи — незмінний `FileSystemSnapshot` у `StateFlow` репозиторію. Екран керується одним `AppScreen`: це перемикання активного повноекранного Compose-вмісту, а не набір одночасно активних системних вікон.
* Метадані файлів зберігає Room. Вміст зберігається як SHA-256 адресовані blobs у приватному сховищі. Операції читання й запису запускаються на `Dispatchers.IO`, серіалізовані `Mutex`; кожна зміна записує нові blobs, транзакційно оновлює Room і тільки потім публікує snapshot.

## Підтверджені вузькі місця й виконані зміни

| Компонент | Причина | Зміна |
| --- | --- | --- |
| Paint | На кожний рух пальця створювався повноекранний `Bitmap` і заново промальовувалася вся історія штрихів. Це створювало значні виділення пам'яті й GC. | Завершені штрихи кешуються в bitmap тільки після завершення дії. Поточний штрих та крива малюються одразу в Canvas без нового повноекранного bitmap. PNG-кодування й декодування винесено на `Dispatchers.Default`; тимчасові bitmap звільняються. |
| Початкове наповнення папок | Декодування та JPEG-кодування вбудованих зображень виконувалося в `LaunchedEffect` на головному потоці. | Винесено на `Dispatchers.Default`; читання MP3 — на `Dispatchers.IO`. |
| Перегляд фотографій | Зображення декодувалося під час кожної recomposition і не мало явного звільнення bitmap. | Зображення декодується один раз у фоновому потоці та звільняється, коли екран змінюється. |
| Музичний плеєр | Копіювання MP3 з репозиторію до cache-файлу робилося на головному потоці. | Копіювання перенесено на `Dispatchers.IO`. |
| Браузер | Читання файлів для завантажень відбувалося у coroutine головного потоку; `WebView` не знищувався після закриття. | Читання asset перенесено на `Dispatchers.IO`; на звільненні `AndroidView` зупиняється завантаження, очищається історія й викликається `destroy()`. |
| Перший екран браузера | Створення `WebView` змінювало Compose state під час вимірювання AndroidView. Це є встановленою за кодом причиною нестабільного першого layout; точне відтворення потребує планшета. | Початкова сторінка завантажується напряму в `factory`; Compose state отримує посилання у `update`. Верхня панель більше не залежить від мутації стану під час вимірювання. |
| Навігація | На кожну recomposition створювалися нові списки вузлів для екранів. | Список вузлів кешується на рівні snapshot. Також додано вимірювання запиту й першого кадру кожного екрана. |

## Пункти, які залишаються для вимірювання

* `LearningFileRepository.persist` навмисно переписує всі рядки метаданих у Room під час кожної файлової операції. Воно працює поза UI-потоком і гарантує атомарність, але може бути помітним із великою кількістю файлів. Оптимізація до диференційних операцій вимагала б зміни моделі збереження, тому не виконувалась без вимірів.
* Провідник використовує звичайний прокручуваний `Column`, а не lazy-список. Для типового навчального набору це не має бути вузьким місцем; за сотень файлів необхідно перевірити на планшеті.
* Word розбиває документ на сторінки й оновлює текст документа при введенні. Це потенційно дорожче за Блокнот для великих документів; зміна на один редактор потребує окремого погодження, бо змінює модель пагінації.
* Немає складних нескінченних анімацій чи важких візуальних ефектів, тому окремий Lite Mode зараз не дасть виграшу, співмірного з ризиком різної поведінки. Реалізовані оптимізації застосовуються на всіх пристроях і не змінюють вигляд.

## Вимірювання на планшеті Android 9

Підставте серійний номер пристрою замість `SERIAL`, якщо підключено більше одного планшета.

```powershell
adb -s SERIAL devices
adb -s SERIAL logcat -c
adb -s SERIAL shell am force-stop ua.school.windowsdesktop
adb -s SERIAL shell am start -W -n ua.school.windowsdesktop/.MainActivity
```

Команда `am start -W` показує час запуску. У debug-збірці код додатково пише в Logcat тег `DesktopPerf`: час до першого кадру, час відкриття екрана, доступну системну RAM, Java heap та агреговані тривалості кадрів.

```powershell
adb -s SERIAL logcat -v time DesktopPerf:I *:S
```

Для кожного сценарію (холодний запуск, Провідник, Paint, Блокнот, браузер) виконайте: скиньте `gfxinfo`, пройдіть сценарій 20–30 секунд, потім збережіть результат.

```powershell
adb -s SERIAL shell dumpsys gfxinfo ua.school.windowsdesktop reset
adb -s SERIAL shell dumpsys gfxinfo ua.school.windowsdesktop
adb -s SERIAL shell dumpsys meminfo ua.school.windowsdesktop
adb -s SERIAL shell top -b -n 1 -o PID,CPU,RES,ARGS | grep ua.school.windowsdesktop
```

Для аналізу UI-потоку та пропущених кадрів запишіть короткий trace під час малювання в Paint або відкриття браузера:

```powershell
adb -s SERIAL shell atrace --async_start -b 8192 gfx view sched freq am wm
# Виконайте сценарій на планшеті протягом 10–20 секунд.
adb -s SERIAL shell atrace --async_stop -b 8192 gfx view sched freq am wm > trace.html
```

Порівнюйте однаковий сценарій на одній і тій самій збірці до й після змін. Числових результатів без запуску на фізичному UNOWHY не наведено.

## Перевірка змін

* Перевірено `git diff --check`.
* Спроба `:app:compileDebugKotlin` у поточному середовищі зупинилась до компіляції через неможливість клієнта під'єднатися до локального Gradle daemon. Повторіть у звичайному PowerShell із кореня проєкту:

```powershell
. .\scripts\Use-LocalToolchain.ps1
.\gradlew.bat --no-daemon assembleDebug
```

* Перед передаванням на планшети необхідно перевірити: запуск, відкриття кожної основної програми, малювання й збереження/відкриття PNG, редагування та збереження тексту, завантаження зображення й казки, закриття та повторне відкриття браузера.
